Paths are to the upstream repositories listed in the first table, as linked in the snbp topic refs.

Date: 2026-10-29. Read-only survey to inform the WCT ~trig/~ streaming contract.

** TriggerPrimitive
 *v1* (used by dunetrigger; ~DDF/.../trigger/TriggerPrimitive.hpp:53-69~, ~Types.hpp:20-55~)

| field                 | type                         | notes                                            |
|-----------------------+------------------------------+--------------------------------------------------|
| ~version~             | ~version_t~ = ~uint16_t~     | ~s_trigger_primitive_version = 1~ (~:56~)        |
| ~time_start~          | ~uint64_t~                   | DTS ticks                                        |
| ~time_peak~           | ~uint64_t~                   | absolute DTS ticks                               |
| ~time_over_threshold~ | ~uint64_t~                   | a duration in DTS ticks                          |
| ~channel~             | ~channel_t~ = ~int32_t~      |                                                  |
| ~adc_integral~        | ~uint32_t~                   |                                                  |
| ~adc_peak~            | ~uint16_t~                   |                                                  |
| ~detid~               | ~detid_t~ = ~uint16_t~       |                                                  |
| ~type~                | ~enum class Type~ (int)      | kUnknown/kTPC/kPDS (~:32-37~)                    |
| ~algorithm~           | ~enum class Algorithm~ (int) | kUnknown/kTPCDefault (~:42-46~)                  |
| ~flag~                | ~uint16_t~                   | bit names ~FlagBits::kSomehowBad~ ... (~:75-90~) |

Not packed; by member layout it is 56 bytes (computed, no static_assert in source).
dunetrigger fills ~time_over_threshold = hit_tover * 32~ and
~time_peak = start + (i_t - tover + peak)*32~ with ~ADC_SAMPLING_RATE_IN_DTS = 32~
(~DT/dunetrigger/TriggerSim/TPAlgTools/TPAlgTPCTool.hh:15~,
~TPAlgTPCRunningSum.hh:162-164~).

 *v2* (~TDF/include/trgdataformats/TriggerPrimitive.hpp:31-84~), introduced in
trgdataformats v2.0.0 (2025-03-27; commits ~d31c249~ and ~58b4351~, 2025-03-24, replaced
~time_over_threshold~ and ~time_peak~):

#+begin_example
uint64_t version : 8;                 // s_trigger_primitive_version = 2   (:33)
uint64_t flag : 8;
uint64_t detid : 8;
uint64_t channel : 24;                // invalid = 0xFFFFFF                 (:38)
uint64_t samples_over_threshold : 16; // invalid = 0xFFFF                   (:36)
uint64_t time_start : 64;
uint64_t samples_to_peak : 16;        // invalid = 0xFFFF                   (:37)
uint64_t adc_integral : 32;
uint64_t adc_peak : 16;
#+end_example

- 24 bytes, asserted (~:34~, ~:96~); little-endian only (~:99~); standard-layout and
  trivially copyable (~:102-103~). No ~type~ or ~algorithm~ field.
- ~operator<~ orders by ~(time_start, channel)~ (~:81-83~); ~get/set_timestamp~ = ~time_start~.
- ~samples_*~ are in *ADC samples*, not DTS ticks. The DAQ TPG converts using the
  frame's tick spacing: ~tp.time_start = (t - tp.samples_over_threshold) * m_sample_tick_difference + timestamp~
  (~TPG/include/tpglibs/TPGenerator.hpp:117-118~), with
  ~samples_tick_difference = 32~ for WIBEth (~FDR/include/fdreadoutlibs/DUNEWIBEthTypeAdapter.hpp:99~).
  ~samples_over_threshold~ is set directly from the AVX counter
  (~TPG/src/AVXPipeline.cpp:83~); ~samples_to_peak~ is relative to the TP start (~:82~).
- Clock (comment only): ~timestamp_t~ is "timing system clock ticks (50 MHz for
  ProtoDUNE-I, 62.5 MHz for ProtoDUNE-II and DUNE FD)" (~TDF/include/trgdataformats/Types.hpp:34-38~).
- The 32 ticks/sample constant is *hard-coded throughout triggeralgs develop* with
  ~FIXME~ notes, for example ~TA/src/TAMakerSupernovaAlgorithm.cpp:27,34~,
  ~TAMakerDBSCANAlgorithm.cpp:52,63~, ~TAMakerPrescaleAlgorithm.cpp:29-30~,
  ~TAMakerHorizontalMuonAlgorithm.cpp:165-166~, ~TAMakerProtoDUNEBSMWindowAlgorithm.cpp:163-164~,
  and as ~const uint16_t k_sample_to_dts_ticks = 32~
  (~TA/include/triggeralgs/ADCSimpleWindow/TAMakerADCSimpleWindowAlgorithm.hpp:62~).
  SWIFT's thresholds are still in TPv1 units: ~min_samples_over_threshold~ default 256
  "8 * 32 DTS ticks while still using TPv1 FIXME" (~TA/src/TAMakerSWIFTAlgorithm.cpp:22~)
  but compared against ~samples_over_threshold~ (~:37~), which is now in samples.
- ~trigger~ knows nothing about samples: ~TriggerPrimitiveTypeAdapter::expected_tick_difference = 1~
  (~TRG/include/trigger/TriggerPrimitiveTypeAdapter.hpp:61~).

Types also changed in v2.0.0 (~git diff v1.2.5 v2.0.0 -- Types.hpp~):
~detid_t uint16→uint8~, ~channel_t int32→uint32~ (+ ~channel_diff_t int32~),
~version_t uint16→uint8~. Develop adds ~TypeDefaults::s_invalid_*~ and
~g_whole_detector = 0xFE~ (~TDF/.../Types.hpp:61-69~).

* The DAQ streaming contract (trigger package)
There are two generations. The answer to "is there a coverage concept?" is: *yes in
DAQ v4 (2021 to Feb 2024), removed in DAQ v5*.

** ~Set<T>~: the v4 envelope (still present in develop, mostly unused)
~TRG/include/trigger/Set.hpp:21-62~:

#+begin_example
template<class T> class Set {
  enum Type { kUnknown = 0, kPayload = 1, kHeartbeat = 2 };
  uint64_t seqno;          // "An incremental count of how many Sets have been produced by this source"
  run_number_t run_number;
  SourceID origin;         // "Identify the instance creator/stream/source of this set"
  Type type;               // "Whether this Set is a regular bag-of-objects or a heartbeat"
  timestamp_t start_time;  // "The earliest timestamp inspected to form this Set"
  timestamp_t end_time;    // "The latest timestamp inspected to form this Set"
  std::vector<T> objects;
};
#+end_example

~TPSet = Set<TriggerPrimitive>~ (~TRG/include/trigger/TPSet.hpp:20~), likewise ~TASet~,
~TCSet~. The header comment ("A set of TPs or TAs in a given time window, defined by
its start and end times", ~Set.hpp:21-23~) plus "earliest/latest timestamp /inspected/" is
the coverage concept: an interval of data time the producer has looked at, not
the extent of the contents.

** v4 pipeline (~TRG@v4~, deleted in ~f0edce8~, 2024-02-17, first released in trigger v2.0.0 / coredaq v5.0.0)
#+begin_example
readout TP handler --TPSet(payload|heartbeat)--> [TPZipper] --> TriggerActivityMaker
  --TASet--> [TAZipper] --> TriggerCandidateMaker --TC (bare)--> ModuleLevelTrigger --TD-->
#+end_example

Module classes: ~TriggerActivityMaker : TriggerGenericMaker<Set<TP>, Set<TA>, TAM>~
(~TRG@v4:plugins/TriggerActivityMaker.hpp:25-28~);
~TriggerCandidateMaker : TriggerGenericMaker<Set<TA>, TC, TCM>~
(~TRG@v4:plugins/TriggerCandidateMaker.hpp:25-27~). TCs were not wrapped in sets and
carried no heartbeats.

 *Who set start/end on TPSets (readout side).* ~fdreadoutlibs~ ~TPCTPRequestHandler::send_tp_sets()~
(added ~1edb8a8~ 2023-05-31 "add hearbeat TPSets", moved into ~trigger~ in ~1aef025~
2024-02-17); the identical logic survives as ~TRG/src/TPRequestHandler.cpp:49-121~:

- Window ~[m_start_win_ts, m_end_win_ts]~ with
  ~m_end_win_ts = newest_ts_in_latency_buffer - m_ts_set_sender_offset_ticks~ (~:79-80~);
  offset is 6 250 000 ticks = 100 ms (~TRG/src/trigger/TPRequestHandler.hpp:73~).
- TPs in the window come from ~get_fragment_pieces(start, end)~ on the time-sorted skip-list
  latency buffer (~:81~); boundary inclusivity lives in datahandlinglibs (unverified).
- ~type = num_tps > 0 ? kPayload : kHeartbeat~ (~:85~).
- Heartbeats keep the window as ~start_time/end_time~ (~:87-88~); *payload sets have
  start/end overwritten with the first and last TP ~time_start~* (~:97-101~). So on this
  path only heartbeats carry the window.
- Next window starts at the previous end: windows are contiguous (~:112~).
- ~seqno~ increments per set (~:89~); send is non-blocking and a full queue drops the set
  with a ~DroppedTPSet~ warning (~:105-107~).

~FakeTPCreatorHeartbeatMaker~ (~TRG@v4:plugins/FakeTPCreatorHeartbeatMaker.cpp:123-195~)
inserted a zero-length heartbeat (~start_time == end_time == next payload start_time~,
~:190-192~) before a payload whenever more than ~heartbeat_interval~ had passed since
the last heartbeat (~:180-183~). It assumes inputs "are already ordered by start_time" (~:177~).

 *Heartbeat meaning (stated explicitly).* ~TRG@v4:plugins/TriggerZipper.hpp:210-229~:
"The heartbeat TSET encodes the information 'you have seen all TSETs with start times
earlier than 100 (but none later)', so it must be output before the payload TSETs with
the same start time." ~TriggerGenericMaker~ comment: "We've got a heartbeat for time T,
so we know we won't receive any more inputs for times t < T"
(~TRG/src/trigger/TriggerGenericMaker.hpp:352-357, 529-532~). So a heartbeat's
~start_time~ is a *watermark*: an exclusive lower bound on future ~start_time~s.

 *Merging multiple streams: the zipper* (~TRG@v4:plugins/zipper.hpp~, ~TriggerZipper.hpp~).

- ~zipper::merge~ is a k-way min-heap merge on an ~ordering~ key with per-stream
  (~identity~) occupancy tracking (~zipper.hpp:37-56, 67-92~).
- Ordering key = ~start_time << 1 | (type != kHeartbeat)~, so on ties heartbeats
  sort before payloads (~TriggerZipper.hpp:231-233~). Identity = subsystem plus id of
  ~origin~ (~:48-52~).
- Drain policy: output the heap top only when the queue is "complete", meaning every
  known stream other than the top's has at least one queued element
  (~zipper.hpp:261-339~). With ~max_latency_ms > 0~ (~drain_prompt~) a stream that has
  been silent (wall clock since ~last_seen~) for longer than the max latency is treated as
  represented, which bounds latency (~:300-327~). With ~max_latency_ms == 0~
  (~drain_waiting~) it waits indefinitely (~TriggerZipper.hpp:273-282~).
  ~cardinality~ = expected stream count; ~tolerate_incompleteness~ and
  ~completeness_tolerance~ allow k-1 completeness (~zipper.hpp:330-335~;
  schema ~TRG@v4:schema/trigger/triggerzipper.jsonnet:19-27~).
- *Late data*: ~feed()~ rejects a node whose ordering is below the last drained
  ~origin~ (~zipper.hpp:149-153~). The zipper counts and warns "tardy" sets and drops them
  (~TriggerZipper.hpp:235-244~).
- On output the zipper re-stamps ~origin.id = element_id~ and a fresh ~seqno~
  (~TriggerZipper.hpp:255-258~).

 *Consuming sets: ~TriggerGenericMaker~* (header still in develop at
~TRG/src/trigger/TriggerGenericMaker.hpp~, but nothing includes it: dead code).

- ~TimeSliceInputBuffer~ (~TRG@v4:src/trigger/TimeSliceInputBuffer.hpp:23-77~) groups
  consecutive input Sets with equal ~start_time~ (the zipped parts of one slice). A Set
  with a different ~start_time~ closes the slice. The slice is concatenated and
  *sorted by ~time_start~* (~:74~) before being fed object by object to the maker.
  Mismatched ~end_time~ in one slice gives an ~InconsistentSetTimeError~ warning (~:66-68~).
- Payload input: warn ~OutOfOrderSets~ if ~start_time~ goes backwards, but still process
  it (~TriggerGenericMaker.hpp:338-342~).
- Heartbeat input (~:351-389~): flush the input buffer (fatal ~OutOfOrderSets~ if the
  buffered ~end_time > heartbeat.start_time~, ~:362-365~), process it, then
  *call ~maker->flush(in.end_time, elems)~* (~:383~), and forward a heartbeat to the
  output buffer. This was the only caller of triggeralgs ~flush()~.
- Set-to-bare output (TC maker): the heartbeat flushes the input buffer and the maker but
  does not propagate (~:526-544~).

 *Producing sets: ~TimeSliceOutputBuffer~* (~TRG@v4:src/trigger/TimeSliceOutputBuffer.hpp~).
This is the closest DAQ analogue to the proposed coverage:

- Output windows are *aligned to multiples of ~window_time~*
  (default 625 000 ticks = 10 ms, ~:51~; config "Windows start at a multiple of this
  value", ~TRG@v4:schema/trigger/triggeractivitymaker.jsonnet:16-19~). The first window
  start is ~floor(first.time_start / W) * W~ (~:63-67~).
- A payload TASet has ~start_time = k*W~, ~end_time = (k+1)*W~ (~:154-157~) and contains
  the objects with ~start <= time_start <= end~ (~:158-166~). Both ends are inclusive,
  so an object exactly on a boundary goes into the earlier window.
- *Window closing is data-time driven*: ~ready()~ when
  ~largest_seen_time - (next_window_start + W) > buffer_time~ (~:118-125~), where
  ~largest_seen_time~ is updated by both objects and heartbeats (~:74-76, 98-100~).
  There is no wall-clock timeout.
- *Late objects*: an output object with ~time_start < next_window_start~ is dropped with
  ~TardyOutputError~ (~:69-71~); same for late heartbeats (~:90-92~).
- Heartbeats must be *aligned* (~start_time % W == 0~) or are dropped with
  ~UnalignedHeartbeat~ (~:93-95~). Heartbeats are zero-duration, live at window
  boundaries, and are emitted before the window that starts at the same time (~:137-152~).
  (Readout heartbeats from ~TPCTPRequestHandler~ were not aligned, so after the TA maker
  they would have been dropped. This is an observation from the code; I did not see it
  documented.)
- *Empty payload windows are not emitted*: only heartbeats or non-empty payload Sets are sent
  (~TriggerGenericMaker.hpp:409-424~). "No news" is therefore conveyed only by heartbeats.
- At stop, ~drain(true)~ drops buffered output because it is "stale and will cause tardy
  warnings from the zipper downstream" (~TriggerGenericMaker.hpp:193-201~).

** v5 / develop pipeline: no sets, no heartbeats, no coverage
Commit ~f0edce8~ (2024-02-17, "use the readoutlibs data structures for the creation of
modules with latency buffer, request handler and processor") deleted the zippers, the
TimeSlice buffers, the TA/TC maker modules, the heartbeat maker, TCBuffer and
ModuleLevelTrigger. Develop modules (~TRG/CMakeLists.txt:61-66~):
~DataSubscriberModule~, ~TriggerDataHandlerModule~, ~FixedTimeTCMakerModule~,
~RandomTCMakerModule~, ~MLTModule~, ~TPReplayModule~.

Flow:

#+begin_example
TPG (fdreadoutlibs) --vector<TPTypeAdapter> per (readout unit, plane)--> TriggerDataHandlerModule[TPProcessor]
   --TA (bare, one message per TA)--> TriggerDataHandlerModule[TAProcessor]
   --TC (bare)--> TriggerDataHandlerModule[TCProcessor] --TriggerDecision--> MLTModule --> DFO
#+end_example

- *TP producer*: ~TPCEthFrameProcessor::find_tps~ (~FDR/include/fdreadoutlibs/detail/TPCEthFrameProcessor.hxx:719-774~)
  appends TPs per plane in the order the TPG emits them, which is the order hits /close/,
  not sorted by ~time_start~. It sends a plane's vector when a frame-count or TP-count
  limit is reached (~:749-771~; config ~:170-177~). Each sink corresponds to one plane
  (~:135-138~). The batch carries no time interval, so an empty batch is never sent
  (~:758-760~). A failed non-blocking send drops the batch with a warning (~:765-767~).
- *Data handler*: ~TriggerDataHandlerModule::create_readout~ builds a
  ~TriggerDataHandlingModel<Adapter, RequestHandler, SkipListLatencyBuffer, Processor, InputType>~
  for TP, TA and TC (~TRG/plugins/TriggerDataHandlerModule.cpp:64-131~). Every stage
  therefore has a time-indexed *latency buffer* (skip list ordered by ~operator<~:
  TP ~(time_start, channel)~ ~TriggerPrimitiveTypeAdapter.hpp:25-28~; TA
  ~(time_start, channel_start)~ ~TAWrapper.hpp:44-48~; TC ~(time_start, type)~
  ~TCWrapper.hpp:43-44~). The buffer serves DataRequests for TP/TA/TC fragments by time
  window.
- ~transform_payload~ keeps only the objects: a ~TPSet~ input is reduced to its
  ~objects~ and ~type/start_time/end_time/seqno~ are discarded
  (~TRG/include/trigger/detail/TriggerDataHandlingModel.hxx:20-39~). A heartbeat TPSet
  becomes zero TPs.
- *Algorithm invocation*: ~TPProcessor::conf~ registers one postprocess task per TA
  algorithm (~TRG/src/TPProcessor.cpp:100-110~). ~find_ta~ calls ~taa->operator()(tp, tas)~
  for every TP and sends each TA immediately (~:152-175~). The same pattern is used for TA→TC
  (~TRG/src/TAProcessor.cpp:101-107, 150-172~). Tasks run in arrival order, not latency-buffer
  sort order (unverified; this is TaskRawDataProcessorModel in datahandlinglibs).
- *Multiple inputs*: no zipper. A TAProcessor fed by several TPProcessors gets their TAs
  interleaved by network arrival. There is no merge-sort and no completeness or watermark
  logic. Only the latency buffer is time sorted, for requests.
- *~flush()~ is never called in develop.* The only callers are in the dead
  ~TriggerGenericMaker.hpp:383,544~ (grep over ~TRG~). An algorithm's open window is
  emitted only when a later input closes it.
- *TPSet still exists in develop* for the TP request handler's periodic transmission
  (~TRG/src/TPRequestHandler.cpp:49-121~, e.g. for TP-stream recording) and for
  ~DataSubscriberModule~ with input type "TPSet" (~TRG/plugins/DataSubscriberModule.cpp:83-88~).
  The trigger chain itself ignores the set metadata.
- Ordering checks: no assertion on input time order in ~trigger~ develop. Latency
  monitoring (~TRG/include/trigger/Latency.hpp:79-85~) records only
  ~wallclock_now - data_ts * 16 ns~, as two opmon gauges, ~latency_in~ and ~latency_out~
  (~TPProcessor.cpp:155-164~).
- Dropped outputs: every inter-stage send is ~try_send(..., s_no_block)~. On failure there
  is a warning and a counter (~TADropped~ ~TPProcessor.cpp:165-167~, ~TCDropped~
  ~TAProcessor.cpp:163-165~).

** TC → TD in develop: wall-clock windows (no heartbeat)
~TCProcessor~ (~TRG/src/TCProcessor.cpp~, header ~TRG/src/trigger/TCProcessor.hpp:123-146~):

- Each TC either merges into an overlapping ~PendingTD{contributing_tcs, readout_start, readout_end, walltime_expiration}~
  or starts a new one (~add_tc~ ~:393-461~).
  Overlap is tested on readout windows (~check_overlap~ ~:486-495~). Merging extends
  the window and resets ~walltime_expiration = now + buffer_timeout~ (~:419-438~).
  With ~ignore_overlapping_tcs~, an overlapping TC is dropped instead (~:409-415~).
- *A pending TD closes on wall-clock timeout* (~steady_clock~ ms, ~get_ready_tds~
  ~:497-516~) or when the readout window reaches ~td_readout_limit~ (~:537-547~).
  A sender thread polls every 100 µs (~:343-360~). Data time and heartbeats play no part.
- TC types can be ignored (~:269-281~). Trigger bitwords are AND-masks over TC-type bits
  (~:585-618~). Pending TDs are discarded at stop (~:85-88, 549-561~).
- ~m_send_timed_out_tds~ is read from config (~:137~) but never used in develop. In v4 it
  decided whether a TD overlapping an already-sent TD was sent or dropped
  (~TRG@v4:plugins/ModuleLevelTrigger.cpp:480-500~).
- v4 ~ModuleLevelTrigger~ had the same wall-clock ~buffer_timeout~ logic
  (~TRG@v4:plugins/ModuleLevelTrigger.cpp:431-500, 601-646~), so *TD formation never
  used heartbeats in either generation*.

** Summary: "each port emits in time order"?
- v4: per-stream time order was *expected but not guaranteed*. It was enforced
  by sorting inside a slice (TimeSliceInputBuffer), by the zipper merge (k-way on
  ~start_time~), and by windowed output buffers. Warnings fired on violation
  (~OutOfOrderSets~, ~TardyOutputError~, zipper "tardy") and late items were *dropped*.
  Heartbeats were watermarks (start_time = "nothing earlier will come") and drove both
  ~maker->flush()~ and output-window closure.
- develop: the only ordering guarantee is the latency buffer's sort, which matters for
  data requests. Algorithms see arrival order and assume time order themselves (below).
  There are no watermarks or heartbeats, and windows close on wall clock (TD) or on the
  next input (TA/TC algorithms).

* How a TD addresses data
** TD construction (develop ~TCProcessor::create_decision~, ~TRG/src/TCProcessor.cpp:292-341~)
- ~trigger_timestamp = time_candidate~ of the earliest contributing TC (~:295, 305, 518-535~).
- ~trigger_number~ and ~run_number~ are left 0 and filled by the MLT (~:303-304~).
- ~readout_type = kLocalized~ (~:306~).
- ~trigger_type~ = a 64-bit bitword with one bit per contributing TC type (~:308-311~).
- ~components~ holds one ~ComponentRequest{component = SourceID, window_begin, window_end}~
  per link (~create_request_for_link~ ~:674-688~). The links are every
  ~mandatory_source_ids~ and ~enabled_source_ids~ entry from config (~:117-125~), plus
  group links (~:327-332~). The *same window ~[readout_start, readout_end]~ goes to every link* (~:323-325~).
- Per-TC-type window (~TCReadoutMap~, ~parse_readout_map~ ~:620-635~):
  ~readout_start = time_candidate - time_before~, ~readout_end = time_candidate + time_after~
  (~:452-454~). If the type has no map entry, the window is the TC's own
  ~[time_start, time_end]~ (~:455-458~). Merged TCs take the union of windows (~:425-436~).
- Optional ROI mode: pick link groups at random, weighted by probability, with
  ~trigger_timestamp ± time_window~ (~:773-807~). Group-links parsing is a TODO, so groups are
  empty (~:127-131~).
- HSI path: ~HSISourceModel~ builds TCs with ~time_start = ts - time_before~,
  ~time_end = ts + time_after~ per signal (~TRG/src/trigger/HSISourceModel.hpp:103, 159-160~).
  ~RandomTCMakerModule~ does the same (~TRG/plugins/RandomTCMakerModule.cpp:105-106, 212~).

** MLT (~TRG/plugins/MLTModule.cpp~)
- In conf, builds ~SourceID → Subdetector~ from the session's geo-id map
  (~:98-114~) and a per-subdetector ~(time_before, time_after)~ map
  (~subdetector_readout_map~, ~:116-136~).
- On each TD (~trigger_decisions_callback~, ~:319-410~): set ~run_number~ and
  ~trigger_number~ (~:333-334~). For each ~kDetectorReadout~ component whose subdetector
  has an entry, *overwrite ~window_begin/window_end = trigger_timestamp ∓ before/after~*
  (~:336-351~). So the final per-source window can be per-subdetector rather than per-TC-type.
- If paused or the DFO is busy (~TriggerInhibit~ callback ~:412-420~), the TD is counted
  and dropped (~:391-406~). Otherwise it is sent to every TD output (~:355-379~).
- The trigger number only increments on a successful send (~:379~).

** TD → data
- ~ComponentRequest~ (~DAQDF/include/daqdataformats/ComponentRequest.hpp:25-38~, version 2):
  ~SourceID component; timestamp_t window_begin; timestamp_t window_end;~. The
  ~TriggerRecordHeaderData~ records ~trigger_timestamp~, ~trigger_type~,
  ~num_requested_components~ (~DAQDF/include/daqdataformats/TriggerRecordHeaderData.hpp:44-54~),
  followed by the ComponentRequests.
- The DFO/dataflow turns each ComponentRequest into a DataRequest to the data handler that
  owns that SourceID. The handler answers from its latency buffer by time window
  (~get_fragment_pieces(start, end)~, as used in ~TPRequestHandler.cpp:81~). Trigger's
  own TP/TA/TC data handlers also have SourceIDs, so TP/TA/TC fragments are read out by the
  same mechanism. Dataflow internals are not in refs (unverified).
- The relationship is *time window × SourceID list*. There is no channel-level ROI and
  no reference to which TPs/TAs caused the trigger, except the TC→TA ~inputs~ stored in TC
  fragments and the TA→TP ~inputs~ stored in TA fragments.

* Implications for the WCT contract
1. The proposed ~[begin, end)~ coverage plus empty-set heartbeat is *essentially DAQ v4's
   ~Set<T>~*, but cleaner. v4 mixed meanings: payload TPSets from readout carried the
   first/last TP time while heartbeats carried the window; heartbeats were zero-length
   watermarks while TASet payloads carried aligned ~[kW, (k+1)W]~ windows inclusive at both
   ends; empty payload windows were never sent. A single half-open coverage on every set,
   empty or not, removes these special cases.
2. DAQ v4 heartbeat semantics are "no future set will have ~start_time~ < T". In WCT
   terms, a set with coverage ~[b, e)~ asserts that nothing with time < e remains for that
   stream. That justifies calling ~maker->flush(e)~ and closing output windows, which is
   exactly what v4 did (~TriggerGenericMaker.hpp:383~).
3. For merging N streams, v4's zipper (min over streams, wait for every stream to be
   represented, optional wall-clock staleness) maps to: output watermark = min over inputs
   of their last coverage end. WCT has no wall clock, so the latency escape is not needed.
4. Late or out-of-order data: v4 dropped it with a warning; develop does not detect it.
   TPs from the DAQ TPG arrive in hit-close order, not ~time_start~ order (section 2.3), so
   a TA node that feeds triggeralgs should sort within a coverage window, as
   ~TimeSliceInputBuffer~ did (~:74~).
5. TD formation in the DAQ is wall-clock based (~buffer_timeout~). In WCT the
   data-time equivalent is: close a pending TD once the TC watermark passes
   ~readout_end + buffer~ (in ticks).
